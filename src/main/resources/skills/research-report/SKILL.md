## 适用场景
用户需要一份有结构的调研产出（对比、综述、方案、报告），且信息可能同时来自上传文档和公开网络。

## 工作流：先取证，后成文
1. **拆解问题**：把调研目标拆成 2~4 个待回答的子问题，后续每一步工具调用都应服务于其中一个子问题。
2. **私有证据优先**：先 `document_list` + `rag_search` 检查上传文档里已有的材料，避免网络信息覆盖用户自己的数据。
3. **公开信息补齐**：对文档没有覆盖的子问题，用 `web_search` 找 2~3 个高质量来源，对最相关的 1~2 个 URL 调用 `web_scraping` 获取正文细节。不要只凭搜索结果摘要下结论。
4. **时效敏感信息**：涉及价格、政策、版本、日期等时效信息时，先调用 `date_time` 确认当前日期，并在报告中标注信息获取时间。
5. **成文**：证据齐了再 finish。报告必须区分：私有文档证据（带 [S1] 引用）、网络来源（带 URL）、你的分析推断（明确标注"分析"）。
6. **PDF 交付（仅在用户要求时）**：用户明确要 PDF 才调用 `pdf_generation`，传入完整的 Markdown 报告正文；生成后把下载路径告诉用户。

## 铁律
- 每个子问题至少一条证据；没有证据的子问题在报告中如实写"未找到可靠信息"。
- 网络信息注明来源站点；互相矛盾的来源要并列呈现，不要私自裁决。
- 报告篇幅与问题匹配：简单对比 300 字以内，正式调研报告用完整模板。

## 报告模板
```
# {报告标题}

## 结论摘要
（3-5 条要点，先给结论）

## {子问题一}
（证据 + 分析，引用标注）

## {子问题二}
...

## 局限与建议
（信息缺口、时效性说明、下一步建议）

## 来源清单
- [S1] 私有文档《...》(id=...)
- [W1] 网页标题 — URL（访问日期）
```
